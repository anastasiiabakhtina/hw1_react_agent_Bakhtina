# ReAct-агент для фінансового контролю та управлінського обліку

## 1. Опис проєкту
У межах проєкту розроблено автономного ReAct-агента (Reasoning + Acting) на базі **LangGraph** (`StateGraph`) для автоматизації фінансового контролю та управлінського обліку. Агент працює з LLM-моделлю **`google/gemini-3.8-flash`** через **OpenRouter API**, самостійно планує послідовність дій, викликає валідовані фінансові інструменти, обробляє помилки вхідних параметрів та повертає відповідь у суворо типізованому форматі (`AgentStructuredResponse`). Для надійності в середовищі виконання реалізовано багатошаровий захист (`max_steps`, `timeout`, `LoopDetector`) та повне трасування кроків у JSON.

## 2. Доменна задача
- **Домен:** Фінанси та управлінський облік (контроль доходів, витрат, розрахунок прибутку та бюджетний аудит).
- **Що вирішує агент:**
  - Пошук і фільтрація фінансових транзакцій за звітний місяць (`YYYY-MM`), типом операції (`income`/`expense`) та категорією.
  - Точний розрахунок операційного прибутку, податкового навантаження, чистого прибутку та чистої маржинальності (Net Margin у %).
  - Реєстрація нових доходів і витрат у фінансовому реєстрі з перевіркою коректності сум і категорій.
  - Аудит дотримання лімітів витрат і виявлення перевитрат бюджету.
- **Інструменти (tools):**
  - `get_financial_records` — отримання списку доходів і витрат за період `YYYY-MM` з опціональною фільтрацією за типом і категорією.
  - `calculate_profit_metrics` — обчислення операційного та чистого прибутку, суми податку й рентабельності на основі виручки та витрат.
  - `record_transaction` — додавання нової фінансової операції (доходу або витрати) до реєстру.
  - `analyze_expense_budget` — порівняння фактичних витрат за період із затвердженим лімітом бюджету та розрахунок відхилення.

## 3. Архітектура
- **LLM-провайдер:** OpenRouter API (`base_url="[https://openrouter.ai/api/v1](https://openrouter.ai/api/v1)"`), модель `google/gemini-3.8-flash` (підключена через `ChatOpenAI`, параметр `temperature` залишено за замовчуванням `1.0` для стабільного tool calling у сімействі Gemini 3).
- **Структура графа (`StateGraph`):**
  1. `START → agent`: вузол `agent_node` перевіряє захисні ліміти та викликає LLM із прив’язаними інструментами (`bind_tools`).
  2. `agent → conditional edge (route_after_agent)`: якщо спрацював ліміт безпеки або модель не генерує `tool_calls`, граф переходить у `formatter`; якщо є `tool_calls` — переходить у `tools`.
  3. `tools → conditional edge (route_after_tools)`: вузол `safe_tool_node` перевіряє виклики через `LoopDetector` і `timeout`, виконує інструменти та перехоплює помилки валідації Pydantic у `ToolMessage`. Далі повертає керування в `agent` (або в `formatter` у разі зупинки).
  4. `formatter → END`: вузол `formatter_node` формує фінальну відповідь у структурованому вигляді (`answer`, `confidence`, `sources`) через `with_structured_output`.
- **Захисні механізми (`SafetyGuard`):**
  - `max_steps = 12` (за замовчуванням) — жорстке обмеження кількості ітерацій LLM; при досягненні повертається часткова відповідь зі статусом `stopped_by_guard`.
  - `timeout_seconds = 90.0` (за замовчуванням) — контроль загального часу виконання через `time.monotonic()`.
  - `LoopDetector (max_repeats = 3)` — обчислення MD5-хешу від назви інструменту та відсортованих аргументів; зупиняє виконання при 3 ідентичних викликах поспіль.

## 4. Інструкція запуску
1. Клонувати репозиторій:
   ```bash
   git clone <repo-url>
   cd hw1_react_agent_Bakhtina
   ```
2. Створити та активувати віртуальне середовище (Python 3.11+):
   ```bash
   python3 -m venv venv
   source venv/bin/activate  # для Windows: venv\Scripts\activate
   ```
3. Встановити залежності:
   ```bash
   pip install -r requirements.txt
   ```
4. Налаштувати API-ключ OpenRouter (створити файл `.env` на основі `.env.example` або експортувати змінну):
   ```bash
   cp .env.example .env
   # Додайте свій ключ у .env: OPENROUTER_API_KEY=sk-or-v1-...
   ```
5. Запустити unit-тести інструментів, демонстрацію захисту та прогін тест-кейсів:
   ```bash
   python tools.py        # перевірка Pydantic-валідації та tools
   python agent.py        # генерація trajectory.json та демо захисних лімітів
   python test_runner.py  # прогін 5 тест-кейсів та генерація test_results.json
   ```

## 6. Аналіз результатів

**Чи правильно агент обирав tools?**
Так, у всіх 5 тест-кейсах агент безпомилково обирав релевантні інструменти відповідно до їхніх docstrings і політик у `SYSTEM_PROMPT`. У `TC-001` для простої вибірки витрат модель викликала лише `get_financial_records(period='2026-09', record_type='expense')`. У `TC-002` та `TC-003` модель ефективно використала parallel tool calling, об’єднавши незалежні запити (отримання даних за два місяці одночасно у `TC-002` або запис транзакції та аудит бюджету на кроці 1 у `TC-003`) в один раундтрип.

**Де агент помилявся і чому?**
- У `TC-004` користувач попросив перевірити витрати у неіснуючій категорії `'crypto'`. Агент передав `category='crypto'` у `get_financial_records`, що викликало очікувану помилку `ValidationError` у Pydantic-валідаторі (`FinancialRecordsInput`). Завдяки обгортці `safe_tool_node` граф не впав, а повернув структуроване повідомлення про помилку зі списком дозволених категорій. Агент коректно пояснив користувачу причину відмови, навів перелік валідних категорій (`investments` тощо) та успішно виконав другу частину запиту (`analyze_expense_budget`).
- Архітектурний нюанс логування: у `run_agent` агрегація `tool_calls` збирала записи як із вузла `agent`, так і з вузла `tools`, через що назви інструментів дублювалися у підсумковому масиві.

**Кроки: simple vs complex.**
Кількість ітерацій LLM зростає зі складністю задачі, але сублінійно завдяки підтримці паралельних викликів інструментів у `gemini-3.8-flash`:
- `simple` (`TC-001`): **2 кроки** (1 виклик tool → 1 фінальна відповідь).
- `medium` (`TC-002`): **3 кроки** (2 паралельні виклики отримання даних → 2 паралельні розрахунки прибутку → фінальна відповідь).
- `complex` (`TC-003`): **4 кроки** (запис транзакції + бюджетний аудит → вибірка оновлених записів за період → розрахунок чистого прибутку → фінальна відповідь).

**Чи досягав агент max_steps або timeout?**
- На штатних тестах (`TC-001` – `TC-004`) агент завершував роботу за **2–4 кроки** та **7.0–16.8 секунд**, що значно нижче встановлених порогів (`max_steps = 10..12`, `timeout = 60..90 с`).
- На спеціалізованому тесті `TC-005` було навмисно встановлено жорсткий ліміт `max_steps = 1` для складного квартального аудиту за 3 місяці. Після виконання першої серії інструментів на вході в 2-гу ітерацію `SafetyGuard` зафіксував досягнення ліміту кроків, перевів граф у `formatter_node` та сформував часткову відповідь із 6 зібраними проміжними спостереженнями (`status="stopped_by_guard"`, `confidence=0.4`).

**Залежність часу виконання від складності.**
Час виконання прямо корелює з кількістю звернень до LLM (включно з фінальним викликом `formatter_node` для `structured_output`):
- 2 кроки LLM (`TC-001`): **7 004 мс** (~7.00 с)
- 3 кроки LLM (`TC-002`): **14 137 мс** (~14.14 с)
- 4 кроки LLM (`TC-003`): **16 815 мс** (~16.82 с)
Як видно з `trajectory.json`, локальне виконання Python-інструментів займає **1 мс**, тому понад 99% затримки припадає на мережеві запити та інференс мовної моделі.

**Випадки, коли агент НЕ використав tool, хоч мав би.**
Випадків ігнорування інструментів («галюцинації відповідей без перевірки даних») не зафіксовано. У `TC-004` після отримання `ValidationError` для категорії `'crypto'` агент свідомо не став викликати `get_financial_records` повторно з довільно підібраною категорією (наприклад, `'investments'`), а попросив уточнення у користувача — це відповідає принципу безпечної відмови.

## 7. Висновки та обмеження
- **Що працює добре:** сувора валідація входів через Pydantic v2 (`extra="forbid"`, `@field_validator`), перехоплення помилок у `safe_tool_node` без краху графа, паралельне виконання незалежних tool calls та передбачувана зупинка через `SafetyGuard` із частковою відповіддю.
- **Що можна покращити:** фільтрувати події `tool_calls` у `run_agent` лише за вузлом `tools` (щоб уникнути дублювання з кроком планування `agent`), а також додати збереження стану фінансового реєстру у SQLite або JSON-файл замість оперативної пам’яті (`FINANCIAL_LEDGER`).
- **Відомі обмеження:** дані транзакцій зберігаються in-memory в межах одного запуску процесу; додатковий вузол `formatter` додає 1 виклик LLM (~3–6 с залежно від завантаження API) наприкінці кожного запиту для гарантованої структуризації відповіді.

## 8. Структура файлів
- `tools.py` — Pydantic v2 схеми (`extra="forbid"`, `field_validator`) та 4 фінансові інструменти + unit-тести.
- `agent.py` — LangGraph граф (`StateGraph`) з циклом `agent → tools → agent → formatter` та `Structured Output`.
- `safety.py` — захисні механізми: `SafetyGuard` (`max_steps`, `timeout`) та `LoopDetector`.
- `logger.py` — `TrajectoryLogger` для покрокового запису траєкторії у JSON.
- `test_runner.py` — набір із 5 тест-кейсів різної складності та генерація звіту тестування.
- `trajectory.json` — JSON-лог траєкторії виконання агента (згенеровано).
- `test_results.json` — результати прогону 5 тест-кейсів (згенеровано).
- `requirements.txt` — список залежностей проєкту.
- `.env.example` / `.gitignore` — шаблон змінних середовища та правила ігнорування секретів для Git.
- `README.md` — документація проєкту, інструкція запуску та аналіз результатів.
